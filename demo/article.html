从零搭建一个可维护的前端 Design Token 系统

从三层 Token 模型、TypeScript 类型契约到 Light/Dark 运行时切换，整理一条不依赖具体框架、可以长期维护的工程路径。

技术栈
CSS / TypeScript

Design Token 最容易出现的误区，是把它理解成“把十六进制颜色换成 CSS 变量”。变量只是语法，真正有价值的是建立一份稳定契约：设计可以调整视觉语言，组件可以保持接口不变，业务页面也不需要知道某个蓝色究竟是哪一个色值。

本文使用原生 CSS 与 TypeScript 展示完整路径。即使项目采用 Vue、React 或其他框架，核心分层仍然成立。

完成后，你会得到什么

一套只有主题层包含具体色值、组件只消费语义变量，并且能安全切换 Light/Dark 的最小实现。

01从三层 Token 模型开始

一个可维护的系统至少要区分基础、主题语义与组件别名三层。它们分别回答“尺度是什么”“这个值表达什么”和“组件需要怎样的接口”。

基础层只定义与颜色无关的尺度

字号、间距、圆角、控件高度与动效时间属于基础层。它们可以被多个主题共用，不应该出现任何品牌颜色。

tokens.cssfoundation + semantic
:root {
  --space-4: 16px;
  --radius-md: 12px;
  --control-height-md: 44px;
}

[data-mode="light"] {
  --bg-primary: #f5faff;
  --text-primary: #203846;
  --accent: #2f6f92;
}

.button--primary {
  color: var(--text-on-accent);
  background: var(--accent);
}

02用 TypeScript 固定语义契约

CSS 自定义属性允许任意字符串，这意味着拼写错误通常要到浏览器里才会暴露。将公开 token 列表同步为类型，可以在构建阶段发现缺失或越层引用。

theme-contract.tsTypeScript
export const semanticTokens = [
  "bg-primary",
  "bg-elevated",
  "text-primary",
  "text-secondary",
  "accent",
  "border-strong",
] as const;

export type SemanticToken =
  (typeof semanticTokens)[number];

export type ThemeMap = Record<SemanticToken, string>;
层级允许包含禁止包含
Foundation尺寸、字体、间距、动效品牌颜色、页面名
Semantic背景、文字、状态、边界组件结构
Component少量稳定的组件别名私有色板、业务页面变量

03让运行时只切换模式

单主题产品只需要一个主题入口。运行时通过根节点的 data-mode 在 Light/Dark 之间切换，不要同时把主题名、系统偏好和用户选择揉进一个函数。

mode.tsruntime
const modes = new Set(["light", "dark"]);

export function setMode(mode: string) {
  if (!modes.has(mode)) {
    throw new TypeError(`Unsupported mode: ${mode}`);
  }

  document.documentElement.dataset.mode = mode;
  localStorage.setItem("ui:mode", mode);
}
避免首屏闪色

模式初始化脚本应在主题 CSS 之前同步执行；否则暗色偏好的用户会先看到一次亮色页面。

04用工程边界换取长期自由

Token 系统并不是越多越好。最小可用集合应覆盖页面、文字、交互、状态、边界、阴影与玻璃表面；只有同一种语义反复出现时，才增加组件别名。

  • 具体色值只出现在主题 token 文件。
  • Light/Dark 具有完全一致的 token 路径。
  • 组件不读取 Primitive，也不编码主题名称。
  • 焦点、禁用、错误与加载状态使用同一语义轴。
