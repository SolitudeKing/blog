# 实施路线图

路线图只记录当前基线之后仍需完成的工作。已经落地但尚未通过对应运行环境验证的能力，仍保持“待验收”状态。

## 当前基线

- `web` 提供公开站点与管理后台。
- `server` 提供认证、文章、专题、标签、媒体、公告、站点配置、搜索、RSS 与 sitemap API。
- MySQL 是业务数据唯一可信来源，Redis 用于公开内容与站点配置缓存。
- `deploy` 提供 Compose、Nginx 与健康检查脚本；**MySQL / Redis 由外部托管服务提供**，不在本仓库 Compose 内启动；备份责任由托管方承担。
- 固定专题为“雾里拾笺、微光造物、风过留痕”。
- 当前系统没有异步任务服务；未来只有在真实需求成立时才重新设计。
- `demo` 作为静态设计蓝图长期保留，不参与生产构建。

## P1：上线可靠性

### 认证

- 实现 Refresh Token 服务端持久化、轮换、撤销和会话审计。
- 验证密码变更、登出、过期和多设备场景。
- 在真实 HTTPS 与代理边界下复核 Cookie、CORS、限流和客户端 IP。

### 媒体

- 为上传补充大小、MIME、扩展名与内容校验。
- 建立文章正文、封面、缩略图和媒体记录之间的可靠引用检查。
- 删除媒体时保证数据库与文件处理可恢复，避免产生悬空引用。

### 备份与恢复（外部托管边界）

- 与托管方约定 MySQL 自动备份频率与保留窗口（建议每日全量 + 短期 PITR），每季度至少一次恢复演练并记录结果。
- `api-storage` 上传卷仍由本仓库持有，需补充独立备份（卷快照或对象存储镜像）；与数据库恢复点无强对应关系。
- 恢复演练先在一次性或隔离环境完成；恢复前先停 API、保存数据库与上传卷快照，并补充失败回滚流程。
- 当前应用启动会执行 `CREATE DATABASE IF NOT EXISTS`，托管账号通常无 `CREATE` 权限。建议先在托管方建库；后续引入 `MYSQL_SKIP_CREATE_DB` 开关作为代码层补项。

### 数据库演进

- 继续保留当前 `categories/category_id` 到 `topics/topic_id` 的幂等兼容升级。
- 为后续结构变更引入显式、可审计的迁移版本，减少生产环境只依赖 AutoMigrate。

## 完成定义

一项工作只有同时满足以下条件才可标记完成：

1. 源码、配置和文档表达一致。
2. 自动化检查通过，并覆盖关键失败路径。
3. 在能力所属环境完成验证；部署能力必须在容器环境验证，交互能力必须在真实浏览器验证。
4. 数据变更有备份、迁移、回滚或明确不可逆说明。
5. 没有把本地文件、测试数据、密钥或构建产物带入版本历史。
