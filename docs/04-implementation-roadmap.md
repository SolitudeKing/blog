# 实施路线图

## 总体节奏

建议采用“先打通主链路，再逐步增强”的方式实现。不要一开始就追求所有后台细节和高级动效，优先让文章从后台写入、前台读取、缓存生效、部署可跑。

推荐阶段：

1. 项目初始化。
2. 后端基础设施。
3. 核心内容模型。
4. 前台公开站点。
5. 后台管理台。
6. 媒体、缓存、异步任务。
7. 旧数据迁移。
8. 部署与质量加固。

## 开发实施约束

开发过程按“一个可验证目标，一个清晰提交”推进。每完成一个模块、功能或独立修复，都必须参照 `git-convention` 提交规范创建一次 commit，让项目进度可以直接从 Git 历史中追踪。

提交约束：

- 提交前先检查 `git status --short`、未暂存 diff 和暂存 diff。
- 每次 commit 只包含一个明确目标，例如后端认证、文章管理 UI、分类标签 CRUD、文档更新、部署配置。
- 功能实现、文档更新、纯样式调整、依赖配置、缺陷修复应能独立理解时分开提交。
- 不提交 `.env`、构建产物、缓存、日志、IDE 状态、旧项目目录和其他本地个人配置。
- Commit message 使用 `<type>: <中文描述>`，type 仅使用 `feat`、`fix`、`docs`、`style`、`refactor`、`test`、`chore`、`perf`、`revert`。
- 禁止在 commit message 或正文中加入工具、AI、Agent、模型、生成来源、协作者 trailer 等无关署名。

模块完成标准：

- 对应功能可以本地运行或通过可说明的替代验证。
- 后端改动至少通过 `go test ./...`。
- 前端改动至少通过 `npm run typecheck`，涉及页面或构建配置时通过 `npm run build`。
- 真实数据链路改动应做一次 API 或页面冒烟，并清理测试数据。
- 文档、`.env.example`、进度追踪与新增配置保持同步。
- 验证通过后，按功能模块立即创建 commit，再进入下一项任务。

## Phase 0：准备与约定

目标：确定新项目骨架、代码规范和本地开发方式。

交付物：

- `web` 前端工程。
- `server` Go API 工程。
- `worker` Celery 工程。
- `deploy/docker-compose.yml`。
- `.env.example`。
- 基础 README。
- 代码格式化与 lint 约定。
- CreamyUI 风格 token 初稿：主题、明暗模式、语义颜色、圆角、阴影、间距。

验收标准：

- 本地可以启动 MySQL、Redis、API、Worker、前端。
- 前端能访问 API 健康检查。
- API 能连接 MySQL 与 Redis。

## Phase 1：后端基础设施

目标：搭建 Go 服务基础能力。

任务：

- Gin 路由初始化。
- GORM 数据库连接。
- Redis 客户端。
- 配置加载。
- 结构化日志。
- 统一响应结构。
- 统一错误码。
- 参数校验。
- CORS 中间件。
- Recovery 中间件。
- Request ID 中间件。
- 健康检查接口。
- migration 机制。

验收标准：

- `GET /healthz` 返回服务状态。
- migration 可创建基础表。
- 错误响应格式统一。
- 日志包含 request id、path、latency、status。

## Phase 2：认证与后台权限

目标：替换旧版密钥登录，建立 JWT 管理员体系。

任务：

- `users` 表。
- 首次初始化管理员。
- 密码哈希。
- 登录接口。
- 刷新 token。
- 登出接口。
- JWT middleware。
- 权限 middleware。
- Redis token 黑名单。

验收标准：

- 管理员可以登录后台。
- 未登录访问 admin API 返回 `40101`。
- token 过期可以刷新。
- 登出后旧 token 失效。

## Phase 3：文章、分类、标签主链路

目标：完成博客最核心内容能力。

任务：

- `articles`、`categories`、`tags`、`article_tags` 表。
- 分类 CRUD。
- 标签 CRUD。
- 文章 CRUD。
- 文章状态流转：草稿、发布、私有、归档。
- slug 唯一校验。
- 服务端游标分页、筛选、稳定排序。
- 文章详情公开接口。
- 阅读量 Redis 增量。

验收标准：

- 后台可以新增文章。
- 前台可以读取已发布文章。
- 未发布文章不会出现在公开接口。
- 分类标签关系正确。
- 阅读详情不会每次直接写 MySQL。

## Phase 4：前台公开站点

目标：新版博客可以被访客正常阅读。

任务：

- Vite + Vue3 + TS + Sass 基础工程。
- CreamyUI 风格 token 与全局 Sass 入口。
- 路由分组。
- 公开布局。
- 首页文章列表。
- 文章详情。
- Markdown 渲染。
- 目录导航。
- 归档页。
- 分类页。
- 标签页。
- 关于页。
- 搜索页基础版。
- 自研游标分页、标签、按钮、输入框、空状态、骨架屏。

验收标准：

- 前台不依赖 UI 组件库。
- 基础组件视觉风格与 CreamyUI 的语义 token、圆角、阴影、焦点态保持一致。
- 移动端与桌面端布局可用。
- 文章详情阅读体验完整。
- 首页、归档、分类、标签均来自 API。

## Phase 5：后台管理台

目标：管理员可以通过新版后台完成日常维护。

任务：

- 后台布局。
- 登录页。
- 路由守卫。
- 仪表盘。
- 文章列表。
- Markdown 编辑器。
- 自动保存草稿。
- 发布/下线。
- 分类标签管理。
- 公告管理。
- 站点配置。
- 自研表格、弹窗、抽屉、Toast、确认框。

验收标准：

- 后台不依赖 UI 组件库。
- 后台组件遵循 CreamyUI 的状态完整性和可访问性要求，同时保持管理台信息密度。
- 管理员可以完成文章从创建到发布的完整流程。
- 所有危险操作有二次确认。
- 表单校验错误清晰。

## Phase 6：媒体库、缓存与 Celery

目标：补齐图床、缓存、异步任务能力。

任务：

- 文件上传接口。
- 文件 MIME 和大小校验。
- assets 表。
- 本地文件存储适配器。
- 媒体库页面。
- 图片缩略图任务。
- 文章摘要/目录提取任务。
- sitemap/rss 生成任务。
- 阅读量聚合落库任务。
- 缓存封装与缓存失效。
- 任务列表与任务触发 API。

验收标准：

- 上传图片后可以在文章中插入。
- Celery 可消费任务。
- 图片缩略图异步生成。
- 修改文章后相关缓存自动失效。
- 阅读量能定时聚合到 MySQL。

## Phase 7：旧数据迁移

目标：把旧项目内容迁移到新系统。

任务：

- 读取旧图片文件和 Base64 图片。

- 文章 slug 生成。
- 站点配置迁移。
- 公告迁移。
- 迁移报告。
- 失败重试。

验收标准：

- 旧文章数量与新库一致。
- 已发布文章前台可访问。
- 分类标签关系正确。
- 图片链接可访问。
- 关于内容和社交链接正确。

## Phase 8：部署与质量加固

目标：达到可长期运行状态。

任务：

验收标准：

- 备份可以恢复。
- 公开站点首屏加载体验良好。
- 后台核心流程无阻塞性缺陷。

## 推荐里程碑

里程碑用于判断项目是否进入下一阶段，必须区分“主要里程任务”和“前置工作”。

判定规则：

- 主要里程任务是当前里程碑验收所必须完成的能力，未完成时不能把该里程碑标记为完成。
- 前置工作是为了降低后续阶段风险而提前完成的能力，可以记录为“提前完成”，但不能替代当前里程碑验收。
- 允许提前做后续里程碑的前置工作，但项目状态仍以当前主要里程任务的验收结果为准。
- 每个里程碑完成时，必须在 `docs/05-design-progress.md` 中更新状态、验证记录和对应 commit。

## 风险与控制

| 风险 | 表现 | 控制方式 |
| --- | --- | --- |
| 前端自研组件耗时 | 表格、弹窗、上传、分页重复造轮子 | 只做项目需要的最小能力，不做通用组件库 |
| Celery 与 Go 集成复杂 | 任务投递协议排障困难 | 第一阶段用 task-gateway 或封装清晰的 task client |
| 旧数据编码异常 | 旧注释和部分文本显示乱码 | 迁移脚本支持编码检测，迁移后生成差异报告 |
| 图片双写历史数据 | DB 和文件不一致 | 迁移时优先文件，缺失时回退 Base64 |
| 阅读量写入频繁 | MySQL 热点更新 | Redis 累加，Celery 批量落库 |
| slug 冲突 | 多篇同名文章 | 自动追加短 hash，同时保留原标题 |
| 后台范围膨胀 | 迟迟无法上线 | 先完成文章主链路，其他功能分期 |

## Definition of Done

每个阶段完成时至少满足：

- 主要代码可本地运行。
- 接口有明确响应结构。
- 前端无 TypeScript 阻断错误。
- 后端无明显 panic 风险。
- 核心流程手动验证通过。
- 文档同步更新。
- 新增环境变量写入 `.env.example`。

## 建议开发顺序

1. 建 `server`，先完成 health、config、database、redis。
2. 建 migration，落用户、文章、分类、标签表。
3. 做认证和 admin API。
4. 做文章 CRUD 和公开文章读取。
5. 建 `web`，先做公开站点读取。
6. 做后台登录和文章编辑。
7. 做媒体库。
8. 接入 Redis 缓存。
9. 接入 Celery worker。
10. 写迁移脚本。
11. 做部署和质量加固。
